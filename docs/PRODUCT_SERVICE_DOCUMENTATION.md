# ProductService - Complete Documentation

> Updated to reflect the real code. Previous versions of this document described a ProductService with a flat structure (`Models/`, `Repositories/`, `Services/ProductWorkerServices.cs`) on SQL Server with `Product.Id` as an `int`. The current code is **Clean Architecture + CQRS via MediatR** (`Domain/`, `Application/`, `Infrastructure/`), on **PostgreSQL**, with `Product.Id` as a `Guid`. The structure described below, the class names, and the "⚠️" notes are verified directly against the source code.

## Overview
ProductService is a microservice responsible for managing the product catalog in the distributed system. It handles CRUD operations on products via CQRS (MediatR) and implements a cache-aside Redis cache for single-item reads.

## Architecture

### Architectural Patterns Used
1. **Clean Architecture**: `Domain` (no external dependencies) → `Application` (CQRS, orchestration) → `Infrastructure` (EF Core, Redis) → `Controllers` (thin, only HTTP↔MediatR mapping)
2. **CQRS via MediatR**: every operation is a `Command` (write) or a `Query` (read), each with a dedicated handler
3. **Pipeline Behaviors**: `ValidationBehavior` (FluentValidation) then `LoggingBehavior` wrap every Command/Query, in the order they're registered in `Program.cs`
4. **Repository Pattern**: `IProductRepository` defined in the Domain, implemented in Infrastructure (Dependency Inversion)
5. **Cache-Aside Pattern**: only for `GetProductByIdQuery` — see below, it's not applied to all reads

## Main Components

### 1. Domain - Product Entity

#### Product.cs (real code)
```csharp
public class Product
{
    public Guid Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public decimal Price { get; set; }
    public string Description { get; set; } = string.Empty;
    public bool IsActive { get; set; }
}
```
No Data Annotations here: it's a pure POCO, consistent with the Clean Architecture principle that "the Domain knows nothing about EF Core or validation." The rules (name length, positive price) live in the Application layer's FluentValidation validators, not on the entity.

### 2. Infrastructure - Database Context

#### ProductDbContext.cs (real code)
```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Product>(entity =>
    {
        entity.ToTable("Products");
        entity.HasKey(e => e.Id);
        entity.Property(e => e.Id).HasDefaultValueSql("gen_random_uuid()"); // Guid generated by Postgres
        entity.Property(e => e.Name).IsRequired().HasMaxLength(200);        // 200, not 100
        entity.Property(e => e.Price).HasColumnType("decimal(18,2)");
        entity.Property(e => e.Description).HasMaxLength(500);
        entity.Property(e => e.IsActive).IsRequired();
    });
}
```
**Database**: PostgreSQL 16 (`Npgsql.EntityFrameworkCore.PostgreSQL`), not SQL Server. **Connection String** (Development): `Host=localhost;Port=5432;Database=ProductDb_Dev;Username=postgres;Password=YourStrong_Password123;`. `context.Database.EnsureCreated()` runs at startup — no EF Core migrations.

### 3. Domain/Infrastructure - Repository

`IProductRepository` (Domain) exposes `GetAllAsync`, `GetByIdAsync(Guid)`, `AddAsync`, `UpdateAsync`, `DeleteAsync(Guid)`. `ProductRepository` (Infrastructure) implements them directly against `ProductDbContext`, with no additional logic — no pagination, no repository-side filtering (the `SearchProductsQuery` filters are applied in memory after loading the entire table, see below).

### 4. Application - CQRS (Commands & Queries)

Every Command/Query is a MediatR record with its own handler in a dedicated subfolder:

| Request | Handler | Validator | Note |
|---|---|---|---|
| `CreateProductCommand(Name, Price, Description)` | creates `Product`, saves, populates cache | ✅ `CreateProductCommandValidator` | |
| `UpdateProductCommand(Id, Name, Price, Description, IsActive)` | loads, updates, saves, updates cache | ✅ `UpdateProductCommandValidator` | returns `null` if not found |
| `DeleteProductCommand(Id)` | deletes, removes from cache | ❌ **no validator** | ⚠️ the only Command with no FluentValidation validation |
| `GetAllProductsQuery()` | `GetAllAsync()` from the repository | — | ⚠️ **doesn't use the cache**, always from the database |
| `GetProductByIdQuery(Id)` | cache-aside: cache → DB → populate cache | — | the only query that uses `IProductCache` |
| `SearchProductsQuery(SearchTerm, Category, MinPrice, MaxPrice, IsActive)` | `GetAllAsync()` then filters in-memory with LINQ | — | ⚠️ `Category` is **accepted but ignored** — see below |

#### FluentValidation — real rules
```csharp
// CreateProductCommandValidator / UpdateProductCommandValidator
RuleFor(x => x.Name).NotEmpty().MaximumLength(200);
RuleFor(x => x.Price).GreaterThan(0);                    // Create also adds .LessThan(1_000_000_000)
RuleFor(x => x.Description).MaximumLength(500).When(x => x.Description is not null);
// UpdateProductCommandValidator also adds:
RuleFor(x => x.Id).NotEmpty();
```

#### ⚠️ `SearchProductsQuery` ignores the `Category` filter
```csharp
if (!string.IsNullOrWhiteSpace(request.Category))
{
    _logger.LogWarning("Category filter not yet implemented"); // Italian: "Filtro per categoria non ancora implementato"
}
```
The `category` parameter is accepted from the query string (`GET /api/products/search?category=Electronics`) and passed all the way to the handler, but **it filters nothing** — it only logs a warning and proceeds to return all results as if `category` hadn't been specified. Anyone calling this endpoint expecting a category filter will silently receive unfiltered results.

Furthermore, `SearchProductsQueryHandler` doesn't query the database with the filters: it calls `GetAllAsync()` (which loads the **entire** `Products` table into memory) and then applies `Where(...)` on the LINQ-to-Objects side. It works, but it doesn't scale with a large catalog.

### 5. Pipeline Behaviors — real order

Registered in `Program.cs`:
```csharp
builder.Services.AddTransient(typeof(IPipelineBehavior<,>), typeof(ValidationBehavior<,>));
builder.Services.AddTransient(typeof(IPipelineBehavior<,>), typeof(LoggingBehavior<,>));
```
The registration order determines the execution order: **`ValidationBehavior` wraps `LoggingBehavior` which wraps the handler**. If validation fails, `FluentValidation.ValidationException` is thrown **before** `LoggingBehavior` (and therefore the handler) is ever reached — so an invalid request doesn't produce the `[CQRS] Handling ...` / `[CQRS] Handled ... in Xms` log lines.

`ValidationBehavior` throws nothing if there are no validators registered for that request (`DeleteProductCommand`, all Queries): in that case it passes straight through to `next()`.

The controller explicitly catches `FluentValidation.ValidationException` in `CreateProduct`/`UpdateProduct` and translates it to `400 Bad Request` — there's no global exception filter/middleware doing this.

### 6. Cache Layer - Redis

#### RedisSettings.cs (real code — note carefully what is actually bound)
```csharp
public class RedisSettings
{
    public string ConnectionString { get; set; } = "localhost:6379";
    public string Prefix { get; set; } = "product:";
}
```
⚠️ `appsettings.json`/`appsettings.Development.json` also define `ProductPrefix`, `Host`, `Port`, `Database`, and `TtlMinutes` under `"Redis"`, but **the class has no matching properties** — they aren't bound and have no effect at all. In particular:
- The key actually used is `{Prefix}{id}` — that is, with `Prefix = "dev:product:"` (Development) the key is **`dev:product:{id}`**, NOT `dev:product:item:{id}` as previous versions of this document stated (that was the key built with `ProductPrefix`, which the code doesn't use).
- The **TTL is hardcoded to 5 minutes** in `RedisProductCache.SetProductAsync` (`TimeSpan.FromMinutes(5)`), not the 10 (Development) or 30 (base `appsettings.json`) minutes stated in config.
- The **Redis database is always the default one (db 0)** — both `Program.cs` (`ConnectionMultiplexer.Connect(...)` with no index) and `RedisProductCache` (`multiplexer.GetDatabase()` with no index) ignore `"Database"`.

#### IProductCache.cs
```csharp
public interface IProductCache
{
    Task<Product?> GetProductByIdAsync(Guid id, CancellationToken ct = default);
    Task SetProductAsync(Product product, CancellationToken ct = default);
    Task RemoveProductAsync(Guid id, CancellationToken ct = default);
}
```

#### ⚠️ `InMemoryProductCache` exists but is never used
The project contains an `InMemoryProductCache` implementation (an in-memory dictionary with locking, intended "for development/testing without Redis" per its own comment), but `Program.cs` registers **only**:
```csharp
builder.Services.AddSingleton<IProductCache, RedisProductCache>();
```
There's no way (configuration flag, environment) to activate `InMemoryProductCache` today — it's dead code, not an active fallback. Redis is always required to start the service, even in development.

### 7. Controller - REST API (much broader than just CRUD)

**Base Route**: `/api/products` (with two exceptions that use `~/` to escape the base route — see below)

#### Real CRUD endpoints (these have actual logic behind them)
| Verb | Route | Backing |
|---|---|---|
| GET | `/api/products` | `GetAllProductsQuery` (no cache) |
| GET | `/api/products/{id:guid}` | `GetProductByIdQuery` (cache-aside) |
| POST | `/api/products` | `CreateProductCommand` |
| PUT | `/api/products/{id:guid}` | `UpdateProductCommand` |
| DELETE | `/api/products/{id:guid}` | `DeleteProductCommand` |

#### ⚠️ Additional "e-commerce" endpoints — mostly stubs/placeholders
The controller also exposes a list of endpoints that look like a real e-commerce catalog, but **have no business logic behind them**:

| Verb | Route | What it actually does |
|---|---|---|
| GET | `/api/products/search` | Really filters by `searchTerm`/`minPrice`/`maxPrice`/`isActive`; **`category` is ignored** (see above) |
| GET | `/api/products/featured` | `GetAllProductsQuery().Where(IsActive).OrderByDescending(Price).Take(count)` — "featured" = simply the most expensive |
| GET | `/api/products/bestsellers` | `GetAllProductsQuery().Where(IsActive).Take(count)` — no real sales data, just the first N |
| GET | `/api/products/recommended` | Identical to `bestsellers` — no recommendation logic |
| GET | `/api/products/{productId}/related` | All active products except the requested one, `Take(count)` — no real notion of "related" |
| GET | `~/api/categories` | **Hardcoded list**: `Electronics, Clothing, Home & Garden, Sports, Books, Toys, Food & Beverages` — not derived from real products |
| GET | `~/api/categories/{categoryName}/products` | `categoryName` **is not used to filter** — returns all active products regardless of the value passed |
| GET | `/api/products/brands` | **Hardcoded list**: `BrandA, BrandB, BrandC, BrandD, BrandE` |
| GET | `/api/products/{productId}/reviews` | Checks that the product exists, then **always returns an empty list** — no review persistence exists in this service |
| POST | `/api/products/{productId}/reviews` | Builds a `ProductReview` with `Guid.NewGuid()` and returns it as `201 Created` — **it's never saved anywhere** (no `DbSet<ProductReview>`, no table) |

The two routes with `~/` (`GetCategories`, `GetProductsByCategory`) use ASP.NET Core's absolute-route override to escape the `api/[controller]` prefix (`api/products`) and respond on `/api/categories/...` instead — this is intentional, not an attribute mistake.

Anyone consuming this service expecting real featured/bestsellers/recommended/categories/brands/reviews will find placeholder data or no-op behavior; only CRUD and `search` (partially) have real logic behind them.

### 8. Configuration - Program.cs (real code)

```csharp
builder.Services.AddDbContext<ProductDbContext>(options => options.UseNpgsql(cs));

builder.Services.Configure<RedisSettings>(builder.Configuration.GetSection("Redis"));
builder.Services.AddSingleton<IConnectionMultiplexer>(_ => ConnectionMultiplexer.Connect(/* Redis:ConnectionString */));

builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.AddSingleton<IProductCache, RedisProductCache>();

builder.Services.AddMediatR(cfg => cfg.RegisterServicesFromAssembly(typeof(Program).Assembly));
builder.Services.AddValidatorsFromAssembly(typeof(Program).Assembly);
builder.Services.AddTransient(typeof(IPipelineBehavior<,>), typeof(ValidationBehavior<,>));
builder.Services.AddTransient(typeof(IPipelineBehavior<,>), typeof(LoggingBehavior<,>));

builder.Services.AddCors(options => options.AddPolicy("AllowAll", p => p.AllowAnyOrigin().AllowAnyMethod().AllowAnyHeader()));

var app = builder.Build();
using (var scope = app.Services.CreateScope())
{
    scope.ServiceProvider.GetRequiredService<ProductDbContext>().Database.EnsureCreated();
}
if (app.Environment.IsDevelopment())
{
    app.UseCors("AllowAll");   // ⚠️ see note below
}
app.MapControllers();
```

⚠️ **The `"AllowAll"` CORS policy is applied (`app.UseCors("AllowAll")`) only if `app.Environment.IsDevelopment()`**. In any other environment (`Production`, etc.) the CORS middleware is never activated, even though the policy is registered — a cross-origin call from a browser in production would be blocked. This is probably unintentional (the common pattern is the opposite: a more permissive policy only in dev, more restrictive elsewhere — here instead there's no policy at all outside dev), but it's the real behavior of the code today.

**Service Lifetimes**: `IProductRepository` and `ProductDbContext` are Scoped; `IConnectionMultiplexer` and `IProductCache` are Singleton; the `IPipelineBehavior<,>` are Transient.

## Integration with Other Services

### 1. GatewayBff
- **Named** HTTP client `"ProductService"`, configured from `ServiceUrls:ProductService` (`http://localhost:5198`) in GatewayBff's `appsettings.Development.json`
- Endpoints actually used: `GET /api/products` (catalog aggregation in `GetCatalogQueryHandler`), plus the `POST/PUT/DELETE /api/products` commands from `CommandsController`
- None of the placeholder "e-commerce" endpoints (`featured`, `bestsellers`, `categories`, `brands`, `reviews`) is consumed by GatewayBff today

### 2. OrderService
- No direct integration — OrderService receives price/quantity from the caller at order-creation time, it doesn't fetch them from ProductService

### 3. InventoryService
- Indirect relationship via a shared `ProductId` (`Guid`) — no direct communication

### 4. CustomerWebsite
- Its own `Services/ProductService.cs` (a local wrapper, not this microservice) calls this service directly using the `BaseUrl` configured in `Services:ProductService:BaseUrl` — see `docs/BFF_ARCHITECTURE.md` for details on how that configuration is currently misaligned with the real ports

## Current Limitations (verified in the code)

1. **`GetAllProductsQuery` doesn't use the cache** — every call to `GET /api/products` always hits the database.
2. **`SearchProductsQuery` ignores `Category`** and filters in-memory after loading the entire table — doesn't scale, and the category filter is a silent no-op.
3. **`featured`/`bestsellers`/`recommended`/`related` have no real logic** — they're variations of "take the first N active," not based on sales, popularity, or similarity.
4. **`categories`/`brands` are hardcoded lists**, disconnected from real product data; `GetProductsByCategory` doesn't filter by category at all.
5. **Reviews are never persisted** — the POST endpoint "creates" them only in the response, with no table or storage behind it.
6. **`InMemoryProductCache` is dead code** — not registered, Redis is always required.
7. **Cache TTL hardcoded to 5 minutes**, the Redis `Database` and `ProductPrefix` in `appsettings` are dead config (properties not present in `RedisSettings`).
8. **CORS `"AllowAll"` is never applied outside `Development`** — no active CORS policy in other environments.
9. **Hard delete** (no soft delete), **no pagination**, **no automated tests**.

Before building a real e-commerce experience on top of these endpoints (working category search, featured/bestsellers based on real data, persisted reviews), it's worth explicitly deciding which of these placeholders need replacing and which were only frontend scaffolding.

## Conclusion

ProductService correctly implements Clean Architecture + CQRS for its CRUD core (Create/Read/Update/Delete + cache-aside on `GetById`), with well-structured FluentValidation and pipeline behaviors. Around that core, however, the controller exposes a substantial number of endpoints that look like a "full e-commerce" API but are actually placeholders with no real logic or persistence behind them (featured, bestsellers, recommended, related, categories, brands, reviews) — worth knowing before treating the entire API as production-ready for a frontend.
